# AVITO FINDER — ПРАКТИЧЕСКИЙ PLAYBOOK ДЛЯ АССИСТЕНТА

**Версия playbook:** 1.0.6  
**Для расширения:** Avito Finder `1.0.6-optional-login-observation-report-test-candidate`  
**Назначение:** практическое дополнение к `AVITO_FINDER_OPERATOR_PROTOCOL_AND_ASSISTANT_PROMPT_v1.0.md`.  
**Приоритет:** основной протокол задаёт роли, запреты и границы; этот файл фиксирует точный рабочий синтаксис, порядок действий, статусы и проверенные кейсы реальной работы.

> Если ассистент начинает новую сессию и должен быстро понять, как управлять Avito Finder, читать сначала этот playbook, затем основной протокол.

---

## 1. Модель работы, которую нельзя нарушать

Avito Finder — не агент выбора товара. Расширение только исполняет ограниченные действия в видимом публичном UI Avito и возвращает сырые данные. Ассистент владеет стратегией поиска, критериями, выбором URL для подробного чтения, сравнением и итоговым рейтингом.

Нельзя поручать расширению:

- выбрать лучшие объявления;
- сформировать очередь кандидатов;
- ранжировать варианты;
- решать, что подходит пользователю;
- писать продавцу, открывать телефон, покупать, оплачивать, добавлять в корзину/избранное;
- обходить CAPTCHA;
- использовать скрытые API, произвольный JS, Runtime/Network/Fetch, cookies/localStorage.

Публичная страница Avito и текущий видимый контекст — единственный источник навигационного состояния.

---

## 2. Самое важное правило новой сессии

До технической работы пользователь формулирует задачу и критерии. Технический цикл стартует после явной команды пользователя **«Ищи»**.

После старта каждый следующий план строится только от последней подтверждённой видимой точки, которую вернул Avito Finder.

Если расширение вернуло:

`VISIBLE_AVITO_CONTEXT_CHANGED`

то:

1. считать новый URL, город, запрос и тип страницы источником истины;
2. не восстанавливать старый `tabId`, старый URL или прежнюю вкладку;
3. следующий `AVITO_UI`-план начинать с URL из блока `Текущая точка`;
4. только после этого продолжать фильтры/поиск/сбор.

---

## 3. Какие режимы понимает расширение

Текущий `core.js` допускает четыре режима:

- `INSPECT_FILTERS` — read-only обследование доступных фильтров/controls;
- `DIAGNOSE_DOM` — ограниченный диагностический DOM-снимок выбранной видимой области;
- `SEARCH` — legacy/structured search mode; для обычной современной работы предпочтителен `AVITO_UI`;
- `AVITO_UI` — основной режим конкретных действий с видимым UI и сбора данных.

Для практической работы почти всегда использовать:

- `DIAGNOSE_DOM`, когда неизвестен marker/видимый control;
- `AVITO_UI`, когда control уже известен или нужно собирать объявления/читать явную очередь.

## 4. Базовый каркас AVITO_UI-команды

Рекомендуемый формат:

```text
Цель:
<техническая цель текущего прохода>

Режим:
AVITO_UI

Страница:
https://www.avito.ru/<текущая публичная страница>

Темп:
CONTROL_VISIBLE

Шаги:
<конкретные поддерживаемые действия>

Исключить:
Не писать продавцам. Не показывать телефон. Не покупать и не оплачивать.
```

Для быстрого чтения уже готовой выдачи можно использовать:

`Темп: COLLECTION_FAST`

Допустимые значения `Темп:` только:

- `CONTROL_VISIBLE`
- `COLLECTION_FAST`

Произвольные значения времени в `Темп:` не поддерживаются.

Для последовательного подробного чтения URL есть отдельное поле:

```text
Пауза между карточками:
500 мс
```

Допустимо `0 мс`. Если поле при продолжении незавершённой очереди опущено, сохраняется предыдущая настройка checkpoint.

## 5. Точный синтаксис шагов, который ждёт parser v1.0.6

### 5.1 CLICK

Рабочие формы:

```text
Нажми "Фильтры".
Нажми "Найти".
Нажми data-marker='search-form/submit-button'.
Нажми data-marker='d/checkbox/1'.
```

Допустимые начальные глаголы для click-плана: `Нажми`, `Выбери`, `Открой`, `Раскрой`, `Примени`, `Сбрось` — но обязательно нужен однозначный quoted target или `data-marker`.

Если элемент неизвестен — сначала диагностировать текущую область, а не угадывать marker.

### 5.2 TYPE

Надёжные формы:

```text
Введи "15000" в data-marker='price-to/input'.
Введи "Ryzen" в data-marker='search-form/suggest/input'.
Введи "Златоуст" в "Город".
```

Parser ожидает текст + target. Target может быть наблюдаемым `data-marker` или видимой подписью/placeholder.

### 5.3 COLLECT_MENU

```text
Собери видимое меню.
```

Допустимы варианты с `верни`, `покажи`, `сними`, но рекомендованный стандарт — именно строка выше.

### 5.4 SELECT_OPTION

```text
Выбери "Златоуст" в списке.
```

Использовать после свежего `Собери видимое меню`, если выбор зависит от текущего выпадающего списка.

### 5.5 WAIT

```text
Подожди 2 секунды.
```

Внутренний parser ограничивает такой wait максимумом 5 секунд.

### 5.6 WAIT_FOR

```text
Дождись "Показать объявления".
```

Нужен наблюдаемый target — текст или marker.

### 5.7 COLLECT_LISTINGS — ВАЖНЫЙ СИНТАКСИС

Предпочтительная рабочая форма:

```text
Собери до 20 видимых объявлений.
```

Также parser понимает, например:

```text
Собери первые 10 объявлений.
Верни до 12 видимых объявлений.
```

**Не использовать как каноническую форму:**

```text
Собери до 20 видимых карточек.
```

В текущем parser регулярное выражение ориентировано на stem `карточк`, а словоформа `карточек` не проходит надёжно. В живой сессии это уже приводило к `UI_PLAN_STEP_REQUIRED`. Поэтому стандарт документации: **для первичного сбора всегда писать `объявлений`**.

Лимит одного шага parser ограничивает максимумом 120, но нормальный рабочий срез обычно 10–20.

### 5.8 COLLECT_LISTING_DETAILS

Для текущей уже открытой карточки поддерживается, например:

```text
Собери публичный паспорт текущего объявления.
```

Но основной рабочий путь для анализа нескольких кандидатов — не этот, а явная очередь URL.

### 5.9 COLLECT_EXPLICIT_LISTING_QUEUE

Каноническая форма:

```text
Собери публичные данные лотов из очереди пакетом 8.
```

Перед этим обязательно должен быть блок `Очередь:` с точными публичными URL Avito, выбранными ассистентом.

Максимум явной очереди — 30 URL. Расширение сохраняет порядок и открывает максимум одну дочернюю карточку одновременно.

### 5.10 RESUME_EXPLICIT_LISTING_QUEUE

После вручную решённой CAPTCHA:

```text
Продолжи сбор лотов из очереди после решённой CAPTCHA.
```

Не создавать новую очередь и не перезапускать поиск: продолжать тот же незавершённый checkpoint.

### 5.11 SNAPSHOT / диагностика

Для неизвестной разметки использовать `DIAGNOSE_DOM`, например область `FILTERS_VISIBLE` или `DIALOG_VISIBLE`.

Поддерживаемые диагностические области:

- `PAGE_MAIN_VISIBLE`
- `SEARCH_SURFACE_VISIBLE`
- `SEARCH_INPUT_ANCESTRY_VISIBLE`
- `SEARCH_INPUT_PARENT_VISIBLE`
- `FILTERS_VISIBLE`
- `DIALOG_VISIBLE`
- `LISTING_CARD_VISIBLE`
- `REVIEWS_VISIBLE`

## 6. Канонический workflow поиска товара

### Этап A. Зафиксировать критерии пользователя

Ассистент до запуска должен понимать:

- что ищем;
- географию;
- жёсткий бюджет;
- доставку;
- обязательные/желательные характеристики;
- что важнее при сравнении;
- сколько кандидатов желательно подтвердить.

### Этап B. Найти/подтвердить нужную категорию

Если controls неизвестны — `DIAGNOSE_DOM / FILTERS_VISIBLE`, затем точные clicks по текущим markers/подписям.

### Этап C. Сначала применить жёсткие ограничения

Если пользователь сказал «до 15 000 ₽», **не собирать первичную выдачу до подтверждения ограничения цены**.

Это особенно важно: успешный статус шага `TYPE` означает только, что текст был введён в видимое поле. Он сам по себе не доказывает, что Avito уже применил фильтр к выдаче.

### Этап D. Проверить, что фильтр реально применён

Признаки подтверждения:

1. Avito сменил публичный URL/контекст и расширение вернуло новую текущую точку;
2. в новом URL сохранился публичный фильтр Avito;
3. после сбора все/ожидаемые карточки соответствуют жёсткому ограничению.

Если после лимита `15000` в срезе идут товары за 22 990, 44 990, 53 000 и т.п., фильтр считать **неприменённым**, даже если `TYPE: completed`.

### Этап E. Только после этого — COLLECT_LISTINGS

```text
Собери до 20 видимых объявлений.
```

### Этап F. Ассистент сам выбирает URL

По карточкам выдачи ассистент выбирает конкретные кандидаты. Расширению нельзя писать:

```text
Сформируй очередь из лучших объявлений.
```

Это даст `UI_PLAN_SELECTION_BELONGS_TO_ASSISTANT`.

### Этап G. Подробно прочитать только выбранные URL

Передать `Очередь:` и `COLLECT_EXPLICIT_LISTING_QUEUE`.

### Этап H. Анализировать противоречия

Подробная карточка важнее краткого заголовка, но любое противоречие нужно явно отмечать, а не автоматически «разрешать» догадкой.

Примеры реальных ловушек:

- заголовок обещает `512 GB`, описание говорит `256 GB`;
- заголовок содержит GTX 1650, а описание говорит, что GTX 1650 идёт `+5000 ₽`;
- карточка показывает низкую цену, но это цена базовой конфигурации без RAM/SSD;
- Avito UI показывает кнопку доставки, но продавец пишет «Авито доставки нет»;
- объявление выглядит мощным, но описание сообщает «не выводит изображение»;
- компьютер продаётся без SSD/HDD или с неисправным слотом RAM;
- товар уже `зарезервирован` или `временно нет в наличии`.

Такие детали должны менять рейтинг.

## 7. Рабочий кейс: сначала цена 15 000 ₽, потом поиск

Это эталонный порядок для жёсткого бюджета.

### 7.1 Сначала найти marker цены

Если marker не подтверждён свежей диагностикой:

```text
Цель:
Найти текущие видимые элементы фильтра цены.

Режим:
DIAGNOSE_DOM

Страница:
<текущая подтверждённая страница Avito>

Область:
FILTERS_VISIBLE
```

В проверенной версии поле максимальной цены наблюдалось как:

`data-marker='price-to/input'`

Но marker нельзя считать вечным — если UI изменился, диагностировать заново.

### 7.2 Ввести максимум

```text
Цель:
Установить максимальную цену 15 000 ₽.

Режим:
AVITO_UI

Страница:
<текущая подтверждённая страница>

Темп:
CONTROL_VISIBLE

Шаги:
Введи "15000" в data-marker='price-to/input'.
Подожди 2 секунды.

Исключить:
Не собирать объявления. Не открывать карточки. Не писать продавцам. Не покупать и не оплачивать.
```

### 7.3 Если Avito изменил контекст — принять новый URL

Если получен `VISIBLE_AVITO_CONTEXT_CHANGED`, новый URL является источником истины. В живом кейсе Avito нормализовал ценовой фильтр в собственный параметр `f=...`, содержащий диапазон `0..15000`.

Не возвращаться к старому URL.

### 7.4 Собрать контрольный срез

```text
Цель:
Проверить выдачу после реально применённого лимита 0–15 000 ₽.

Режим:
AVITO_UI

Страница:
<НОВЫЙ URL из текущей точки>

Темп:
COLLECTION_FAST

Шаги:
Собери до 20 видимых объявлений.

Исключить:
Не открывать объявления. Не выбирать и не ранжировать варианты.
```

### 7.5 Проверка ассистентом

Ассистент вручную проверяет цены всех возвращённых карточек.

- Если есть явно превышающие жёсткий максимум — не продолжать выбор кандидатов; фильтр исправить и повторить контрольный сбор.
- Если срез соответствует лимиту — можно переходить к поисковым запросам и подробной очереди.

## 8. Рабочий кейс: поиск по запросу, не потеряв уже применённую цену

После подтверждённого ценового фильтра менять поисковый запрос нужно так, чтобы текущий URL/контекст сохранял ценовой `f`.

Пример:

```text
Цель:
Искать Ryzen внутри уже установленной цены 0–15 000 ₽.

Режим:
AVITO_UI

Страница:
<текущий URL С СОХРАНЁННЫМ f-фильтром>

Темп:
CONTROL_VISIBLE

Шаги:
Введи "Ryzen" в data-marker='search-form/suggest/input'.
Нажми data-marker='search-form/submit-button'.
Подожди 2 секунды.

Исключить:
Не менять ценовой лимит. Не собирать объявления на этом шаге.
```

После возможного `VISIBLE_AVITO_CONTEXT_CHANGED` снова взять URL из `Текущая точка`. Убедиться, что:

- `q=Ryzen` появился/подтверждён;
- ценовой `f` сохранился;
- затем отдельным планом выполнить `Собери до 20 видимых объявлений.`

Так же можно проверять `i5 8500`, `i5 8400` и другие целевые запросы, не снимая бюджетный фильтр.

## 9. Рабочий кейс: подробная очередь выбранных кандидатов

После первичного среза ассистент сам выбирает URL.

```text
Цель:
Подробно прочитать выбранные кандидаты для сравнения.

Режим:
AVITO_UI

Страница:
<текущая подтверждённая выдача>

Темп:
COLLECTION_FAST

Пауза между карточками:
500 мс

Очередь:
https://www.avito.ru/<лот_1>
https://www.avito.ru/<лот_2>
https://www.avito.ru/<лот_3>

Шаги:
Собери публичные данные лотов из очереди пакетом 3.

Исключить:
Не писать продавцам. Не показывать телефон. Не покупать и не оплачивать.
```

Правила:

- URL в `Очередь:` не становятся implicit navigation target основной вкладки;
- порядок сохраняется;
- максимум 30 URL;
- открывается одна дочерняя карточка одновременно;
- расширение не добавляет собственные URL;
- после данных анализ выполняет ассистент.

## 10. География и доставка: как не зациклиться на нестабильном toggle

В живой работе диагностический снимок может показать control вроде `filters/localPriority/toggle`, но точный click иногда возвращает `UI_TARGET_NOT_FOUND` из-за динамической разметки Avito.

Правило:

- один свежий диагностический снимок + одна обоснованная попытка click;
- если optional-control не сработал, не повторять бесконечно один и тот же шаг;
- если требование не жёсткое, применять его аналитически по возвращённым `location` и `delivery`;
- если требование жёсткое, сделать новую диагностику текущего контекста и использовать новый наблюдаемый control.

Например: «Златоуст в приоритете, Россия допустима только с Авито Доставкой» можно реализовать без нестабильного toggle: собрать ограниченную выдачу и ассистентом отфильтровать по городу + подтверждённой доставке.

## 11. OPTIONAL_LOGIN_POPUP_OBSERVED в v1.0.6

Обычное окно входа Avito — не CAPTCHA и не должно закрываться расширением автоматически.

Если worker вернул:

`OPTIONAL_LOGIN_POPUP_OBSERVED`

обязательный порядок:

1. не продолжать обычный TYPE/filters/collection;
2. запросить `DIAGNOSE_DOM` с `Область: DIALOG_VISIBLE` на текущем URL;
3. получить свежий список видимых controls диалога;
4. ассистент выбирает конкретный текущий control закрытия по наблюдаемому marker/label/title;
5. отправить отдельный `AVITO_UI`-план ровно с **одним generic CLICK**;
6. не вводить телефон/email/пароль/код;
7. после закрытия продолжить от нового подтверждённого контекста.

Нельзя использовать старый захардкоженный marker вроде `auth-app/close`: v1.0.6 специально требует наблюдать текущий диалог.

## 12. CAPTCHA

`CAPTCHA_MANUAL_REQUIRED` — жёсткая ручная граница.

Расширение:

- оставляет текущую карточку открытой;
- сохраняет курсор очереди;
- не refresh-ит CAPTCHA;
- не решает и не обходит её;
- не переходит к следующему URL.

Пользователь решает CAPTCHA вручную и сообщает `капча решена`.

Тогда:

```text
Цель:
Продолжить незавершённый сбор по прежней очереди.

Режим:
AVITO_UI

Контекст:
Использовать текущую видимую вкладку Avito.

Пауза между карточками:
1500 мс

Шаги:
Продолжи сбор лотов из очереди после решённой CAPTCHA.

Исключить:
Не обходить CAPTCHA автоматически. Не менять очередь.
```

## 13. Частые ошибки валидатора и правильная реакция

| Ошибка/статус | Что означает | Что делать |
|---|---|---|
| `MODE_UNRESOLVED` | Parser не понял режим | Явно написать `Режим: AVITO_UI` или `DIAGNOSE_DOM` |
| `UI_PLAN_PAGE_REQUIRED` | Нет `Страница:` и не указан явный текущий Avito-контекст | Передать текущий публичный URL |
| `UI_PLAN_STEP_REQUIRED` | Ни одна строка шага не распознана | Использовать канонические формулировки; для списка писать `объявлений` |
| `UI_PLAN_TYPE_TARGET_OR_TEXT_REQUIRED` | TYPE без текста или target | Указать quoted text + marker/placeholder |
| `UI_PLAN_TARGET_REQUIRED` | CLICK без точного target | Диагностировать и дать marker/видимую подпись |
| `UI_PLAN_EXPLICIT_PUBLIC_QUEUE_REQUIRED` | Запрошено чтение очереди, но нет URL | Добавить блок `Очередь:` |
| `UI_PLAN_SELECTION_BELONGS_TO_ASSISTANT` | Расширению поручили сформировать/отобрать список | Ассистент сам выбирает URL |
| `UI_PLAN_FORBIDDEN_ACTION` | В шагах есть запрещённое действие | Удалить сообщения/покупку/оплату/корзину/бронь и т.п. |
| `UI_PLAN_TIMING_PROFILE_NOT_ALLOWED` | Неверный `Темп:` | Только `CONTROL_VISIBLE` или `COLLECTION_FAST` |
| `UI_TARGET_NOT_FOUND` | Наблюдаемый control не найден в момент действия | Не спамить retry; свежая диагностика текущего контекста |
| `VISIBLE_AVITO_CONTEXT_CHANGED` | UI/URL изменился между планами | Новый контекст — источник истины; начать следующий план от него |
| `OPTIONAL_LOGIN_POPUP_OBSERVED` | Публичную поверхность перекрыл login overlay | `DIAGNOSE_DOM / DIALOG_VISIBLE` → один точный CLICK |
| `CAPTCHA_MANUAL_REQUIRED` | CAPTCHA | Только ручное решение, затем resume той же очереди |
| `SEQUENTIAL_CARD_READY_TIMEOUT` | Карточка не стала готовой вовремя | Зафиксировать URL/статус; при необходимости отдельный повторный проход по решению ассистента |

Никогда не писать пользователю, что действие выполнено, если валидатор/worker вернул ошибку.

## 14. Приоритет источников данных при анализе объявления

От сильного к слабому:

1. подробная страница конкретного объявления, прочитанная из явной очереди;
2. structured visible characteristics на подробной странице;
3. полный видимый description;
4. карточка выдачи;
5. заголовок объявления.

Но если два источника внутри одной подробной страницы противоречат друг другу, не выбирать значение молча. Отметить конфликт как риск/неизвестность.

Перед рекомендацией обязательно проверять:

- реально ли рабочее состояние;
- что именно входит в отображаемую цену;
- не является ли цена стартовой ценой базовой комплектации;
- наличие RAM/SSD/HDD;
- доставка/самовывоз;
- резерв/нет в наличии;
- явные дефекты;
- расхождение title vs description;
- продавца/отзывы как дополнительный, но не единственный фактор.

## 15. Минимальный алгоритм будущего ассистента

Если пользователь сказал: «Найди лучший ПК до 15 000 ₽»:

1. Уточнить назначение и географию, если они ещё не известны.
2. Дождаться/использовать уже полученное `Ищи`.
3. Открыть/подтвердить категорию системных блоков.
4. Диагностировать price controls при необходимости.
5. **Сначала** установить `price-to = 15000`.
6. Не верить одному `TYPE: completed`; дождаться/принять текущий URL после изменения контекста.
7. Сделать контрольный `Собери до 20 видимых объявлений.`
8. Проверить, что в срезе нет цен >15 000 ₽. Если есть — фильтр не считается применённым.
9. После валидного бюджета делать тематические запросы, сохраняя `f`-фильтр.
10. Из каждого среза ассистент сам выбирает URL.
11. Читать выбранные URL явной очередью.
12. Исключать broken/reserved/base-price bait/без доставки при жёстком требовании доставки.
13. Если подтверждено >=5 подходящих кандидатов — дать минимум 5 с рейтингом, прямыми ссылками, ценой, локацией/доставкой, характеристиками, плюсами, минусами, рисками и сравнением с лидером.
14. Если <5 — честно дать фактическое число и причину.

## 17. Parser-level reference v1.0.6

На момент этой версии исходники подтверждают следующие лимиты/инварианты:

- до 12 шагов в одном `AVITO_UI` плане;
- до 160 символов в одном TYPE text;
- до 120 объявлений в одном `COLLECT_LISTINGS`, хотя рабочие срезы должны быть намного меньше;
- до 30 URL в explicit queue;
- default explicit queue batch — 30;
- только `CONTROL_VISIBLE` и `COLLECTION_FAST`;
- `WAIT` из текста ограничивается 5 секундами;
- URL очереди канонизируются до `origin + pathname` и не используются как implicit `Страница:`;
- запрещённые действия блокируются локальным валидатором;
- выбор/ранжирование остаются за ассистентом;
- завершённый payload не является постоянной базой; сохраняться может только незавершённый технический checkpoint.

## 18. Что обновлять при новой версии расширения

При появлении v1.0.7+ перед использованием этого файла:

1. сверить `manifest.json` и `version_name`;
2. проверить `VALID_MODES`, `UI_ACTION_TYPES`, timing profiles и лимиты в `core.js`;
3. проверить regex `parseGenericStep`;
4. прогнать tests для command parser;
5. обновить примеры, если изменились markers/синтаксис;
6. не переносить в новую версию устаревшие dynamic markers как вечные правила;
7. сохранить раздел «живые кейсы» и дополнять его новыми подтверждёнными ошибками/решениями.
