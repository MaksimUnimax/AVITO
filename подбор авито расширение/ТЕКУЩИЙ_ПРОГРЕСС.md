### Root cause

В exact v1.0.40 `publicPageInterruptionProbe()` broad regex `/captcha|капч/` выставлял `captcha=true` только из-за helper phrase `для решения капчи`; тот же экран одновременно давал `ip_block=true` по heading. `detectBlock()` проверял CAPTCHA раньше IP-block, поэтому manual CAPTCHA state выигрывал, а исторический IP recovery/reload не запускался.

Старый regression `ip_block_refresh_resilience.test.js` проверял только уже классифицированное состояние `ip_block=true && captcha!==true`, но не пропускал реальный firewall DOM через classifier. Поэтому тест мог быть зелёным при живом дефекте. Нарушены Rules 2/16; прежняя causal трактовка экрана как фактической CAPTCHA нарушала Rule 7.

Историческая authority v1.0.24 прямо устанавливает правильный контракт:

`AVITO_IP_BLOCK -> bounded connection/proxy recovery -> tabs.reload(..., bypassCache) -> retry same plan`.

Recovery/reload code в v1.0.40 не исчезал. До него перестала доходить страница из-за classifier misroute.

## v1.0.41 patch

Поведенчески изменён **только `core.js`**.

Новый invariant:

1. точный IP-firewall heading остаётся `ip_block=true`;
2. generic explanatory mention `капчи/captcha` на IP landing не является фактическим challenge;

5. существующий bounded IP recovery/reload используется без переписывания.

`service_worker.js` и `proxy_manager.js` byte-identical v1.0.40. `manifest.json` и `avito_content.js` изменяют release identity.
