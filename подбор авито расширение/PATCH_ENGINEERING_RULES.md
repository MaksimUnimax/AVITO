# Avito Finder — обязательные правила любого патча

Эти правила являются постоянным контрактом проекта и применяются к каждому следующему патчу без исключений.

## 1. Не чинить ближайший симптом

Перед изменением кода нужно разобрать весь затронутый state machine и доказать первопричину. Цепочки вида `timeout → reload → bypassCache → profile switch → egress check` нельзя продолжать очередным костылём без объяснения, почему система вообще попала в это состояние.

## 2. Проверять именно тот уровень, где существует дефект

Нельзя подменять нужное доказательство косвенным признаком:

- `new document` != `new request`;
- `new request` != `new IP`;
- `new profile` != `new egress`;
- `generic Copy button ready` != `writing block exists`;
- локальный DOM PASS != installed/live E2E PASS.

Тест обязан измерять именно тот инвариант, который заявлен исправленным.

## 3. Локальный PASS не равен рабочему релизу

Любые `72/72`, `100/100`, `134/134`, `342/342` и иные локальные PASS являются только локальной проверкой. Версия считается рабочей только после полного реального сценария в установленном Chrome на том же конечном билде.

## 4. Последний известный рабочий baseline неприкосновенен

Уже доказанно рабочие navigation, explicit queue, cursor, child-tab lifecycle, capture, report delivery, proxy boundaries и другие контракты нельзя переписывать без отдельного доказанного дефекта именно в них.

## 5. Контракт ChatGPT ↔ Finder является API-контрактом

Формат ответа, writing block, ordinary assistant response, generic Copy, local Copy, anchor turn, pinned conversation, validator и report handoff считаются частью протокола. Нельзя самовольно менять один формат на другой и ожидать, что downstream продолжит работать.

## 6. Сначала воспроизведение, потом патч

До изменения кода должен существовать тест или воспроизводимый сценарий, который падает на старой версии и соответствует живому дефекту.

## 7. Причина должна быть доказана

Обязательная цепочка:

`живое наблюдение → состояние state machine → конкретный участок кода → причинная связь → падающий regression test`.

Патч по догадке запрещён.

## 8. Патч должен быть минимальным

Меняется только то, что необходимо для устранения доказанной причины. Параллельные «заодно улучшим» запрещены.

## 9. Тот же дефект обязан исчезнуть в том же сценарии

Недостаточно пройти похожий mock. После патча повторяется исходное воспроизведение.

## 10. Все прошлые реальные баги становятся постоянной регрессией

Новый патч не имеет права возвращать уже закрытый реальный дефект.

## 11. Тестируется конечный билд

Проверяется не только working tree, а именно тот ZIP / unpacked build, который передаётся пользователю. После любой executable-правки финальная проверка выполняется заново.

## 12. Обязателен полный installed end-to-end

Минимальный реальный сценарий:

`действие пользователя → assistant response → capture → validator → Avito action → result → report → тот же ChatGPT chat → готовность принять следующую команду`.

## 13. Любой live FAIL отклоняет патч

Если основной installed/live сценарий падает, патч имеет статус `FAIL / NOT READY`. Нельзя объявлять его рабочим, нельзя добавлять новые функции и нельзя строить следующий релиз поверх непроверенного исправления.

## 14. Proxy остаётся transport layer

Proxy не имеет права менять target URL, порядок explicit queue, cursor semantics, child-tab lifecycle, capture или report delivery.

## 15. Никаких бесконечных ожиданий

Любое ожидание обязано завершаться одним из состояний: `SUCCESS`, `RETRYABLE`, `MANUAL_REQUIRED`, `FAILED_WITH_EXACT_REASON`. Бесконечный polling без terminal condition запрещён.

## 16. Если тест не ловит живой баг, тест недостаточен

Зелёный тест, который был зелёным на сломанной версии, не считается доказательством исправления.

## 17. Exact-source rule

Патч для live-релиза делается только от точного исходника установленной/целевой версии. Если exact source отсутствует или версия в Git расходится с установленной, можно подготовить только diagnostic/backport candidate, но нельзя выдавать его за live-ready patch.

## 18. Обязательный отчёт соблюдения правил для каждого патча

Каждый patch report обязан содержать таблицу:

| Rule | PASS/FAIL | Evidence |
| --- | --- | --- |
| Root cause доказан |  |  |
| Падающий тест до патча есть |  |  |
| Проверяется правильный уровень |  |  |
| Working baseline не затронут |  |  |
| Diff минимален |  |  |
| Старые реальные regression-сценарии пройдены |  |  |
| Конечный билд перепроверен |  |  |
| Installed/live E2E пройден |  |  |
| Exact-source rule соблюдён |  |  |

Отдельно обязательно писать раздел `НАРУШЕННЫЕ ПРАВИЛА`: какие правила были нарушены этим патчем/предыдущим кодом, чем это доказано и что изменено, чтобы нарушение не повторилось.

## 19. Каждый релиз немедленно сохраняется в GitHub

После создания любого нового конечного билда его exact source, installable artifact, manifest/version metadata, SHA-256 и QA-отчёт должны быть сохранены в GitHub в том же релизном цикле. Нельзя оставлять новую версию только во временной среде чата, локальном sandbox или как выданный пользователю ZIP. Репозиторий обязан содержать точную последнюю выпущенную версию до начала следующего патча. Если GitHub отстаёт от выданной версии, дальнейший патч запрещён до восстановления exact-source authority.

## Acceptance

Работа считается выполненной только если тот же самый конечный билд прошёл полный реальный сценарий без ошибок. До этого статус: `NOT READY / LIVE UNVERIFIED`.
